# 自定义选择模式需求文档 — 评审报告

> 评审人：Claude Opus 4.8  
> 评审日期：2026-05-29  
> 针对文档：`docs/自定义选择模式需求文档.md`

---

## 一、总体评价

需求文档简洁地描述了一个有实际业务价值的功能：在 `MarkdownWidget` 中实现更灵活的内容选择交互。核心交互路径（长按 → 自定义菜单 → 选取文字 → 按元素选中 → 复制）表述清晰，向后兼容意识明确。

但文档在 **API 接口定义、元素选中边界规则、交互状态管理、技术约束** 等方面存在显著缺失，若直接进入开发阶段，大概率会因为理解歧义导致返工。以下逐维度展开分析。

---

## 二、优点

1. **向后兼容设计清晰**：明确要求未开启自定义模式时保持现有行为不变，保护存量用户。
2. **交互主路径描述直观**：两阶段菜单的设计思路（先弹功能菜单，再弹复制菜单）易于理解。
3. **选中粒度的设计意图合理**：以 Markdown 块级元素为选中单位，比逐字选中更符合结构化内容的操作习惯。
4. **保留了用户微调能力**：选中后仍可拖动光标调整范围，兼顾了便捷性和灵活性。

---

## 三、问题与建议

### 3.1 API 设计缺失（P0）

#### 3.1.1 开启方式未定义

文档反复提到"开启自定义选择模式"，但从未说明如何开启。需要明确：

- 新增参数的名称、类型、默认值是什么？
- 与现有 `selectable` 参数的关系如何？是互斥、还是叠加？当 `selectable = false` 且自定义选择模式开启时，行为是什么？

**建议**：定义一个配置类，通过组合方式开启：

```dart
MarkdownWidget(
  selectable: true,
  customSelectionConfig: CustomSelectionConfig(
    menuBuilder: ...,
    copyMenuBuilder: ...,
  ),
)
```

当 `customSelectionConfig` 非 null 时即视为开启自定义选择模式。这比新增 bool 参数更具扩展性。

#### 3.1.2 自定义菜单接口完全缺失

"样式支持自定义"和"支持自定义其他功能菜单扩展"是需求的核心卖点，但没有任何接口定义：

- 第一阶段菜单（长按弹出）的构建方式是什么？Builder 回调？菜单项列表？
- 第二阶段菜单（选中后弹出）是否也支持自定义扩展（如"分享"、"翻译"、"朗读"）？
- 默认的"选取文字"菜单项是否可被移除或重新排序？
- 菜单的定位信息（触摸坐标、元素边界）如何传递给 Builder？

**建议**：至少定义如下接口签名：

```dart
typedef FirstStageMenuBuilder = Widget Function(
  BuildContext context,
  LongPressDetails details,      // 包含触摸位置、对应的 markdown 元素信息
  VoidCallback triggerSelectText, // 内置的"选取文字"动作
);

typedef SecondStageMenuBuilder = Widget Function(
  BuildContext context,
  SelectionDetails details,      // 包含选中文本、选区位置
  VoidCallback triggerCopy,      // 内置的"复制"动作
);
```

### 3.2 元素选中规则不完整（P0）

#### 3.2.1 "正文部分"定义歧义

> "如果选中的区域是markdown的元素是正文部分，则将选中全部正文部分"

这里的"正文部分"极其模糊：
- 是指当前 `<p>` 段落？
- 还是所有连续的非标题、非列表段落？
- 如果文档有 10 个段落，点击其中一个就全选 10 个？

从源码看，`MarkdownGenerator.buildWidgets()` 中每个顶层 markdown 节点生成一个独立的 Widget（带 `Padding`），所以合理的理解应该是"选中当前段落"。但文档的措辞"全部正文部分"容易被误解为选中所有段落。

**建议**：改为"选中当前点击处所在的段落（`<p>` 元素）的全部文字"。

#### 3.2.2 多种元素类型未覆盖

| 元素 | 是否定义 | 需要澄清 |
|------|---------|----------|
| 标题 h1-h6 | ✅ | — |
| 段落 p | ⚠️ 歧义 | 见上 |
| 列表项 li | ✅ | 嵌套列表是否包含子项？ |
| 引用 blockquote | ✅ | 嵌套引用选哪一层？ |
| 代码块 pre | ✅ | — |
| **表格 table** | ❌ | 选整个表格？当前单元格？当前行？ |
| **图片 img** | ❌ | 图片是否参与选择？选中后复制什么？ |
| **链接 a** | ❌ | 选中链接文字还是包含 URL？ |
| **水平线 hr** | ❌ | 不可选？跳过？ |
| **行内代码 code** | ❌ | 选所在段落还是只选行内代码？ |
| **复选框 input** | ❌ | 是否可选？ |

#### 3.2.3 嵌套元素的选中粒度

Markdown 中嵌套很常见（引用内含列表、列表项内含代码块）。当用户长按嵌套结构中的文字时，选中的是最内层元素还是最外层容器？

从源码的 `WidgetVisitor` 可以看到，`blockquote` 内部会递归处理子节点（`li`、`p` 等）。如果选中粒度是最外层容器，那么点击引用内的一个列表项会选中整个引用块，这可能不符合用户预期。

**建议**：明确规则为"以最内层的块级元素为选中单位"。例如引用内的列表项，选中的是该列表项而非整个引用块。

### 3.3 交互细节缺失（P1）

#### 3.3.1 菜单生命周期

文档未说明菜单在以下场景的行为：

1. 用户点击菜单外的空白区域 → 菜单是否关闭？
2. 用户滚动 `MarkdownWidget` 的内容 → 菜单是否自动消失？
3. 用户在另一处长按 → 旧菜单是否关闭并弹出新菜单？
4. 选中文字后拖动光标 → "复制"菜单是否保持显示？位置是否跟随选区？
5. 键盘弹出导致布局变化 → 菜单位置如何更新？

**建议**：补充完整的状态机描述，至少覆盖"空闲 → 第一阶段菜单 → 元素选中 → 第二阶段菜单 → 空闲"的所有转换条件。

#### 3.3.2 菜单定位的边界处理

"在用户手按住的位置上方弹出"——但如果长按位置在屏幕顶部怎么办？靠近左右边缘呢？

**建议**：说明是否采用自适应定位策略（类似 Flutter 原生 `TextSelectionToolbar` 的行为）。

#### 3.3.3 手势冲突

当前 `MarkdownWidget` 内部已有多种交互：
- 链接（`LinkNode`）的点击跳转
- 图片的点击/长按
- 复选框的点击切换
- `ListView` 的滚动手势

长按手势与这些交互如何共存？特别是长按一个链接时，是触发链接预览还是弹出自定义菜单？

**建议**：定义手势优先级规则。例如：可交互元素（链接、图片、复选框）区域内长按不触发自定义选择菜单。

---

### 3.4 技术实现层面的关键问题（P1）

#### 3.4.1 触摸位置到 Markdown 元素的映射

这是整个需求的技术核心难点。从源码分析：

1. `MarkdownGenerator.buildWidgets()` 将 markdown 解析为 `List<Widget>`，每个 Widget 对应一个顶层 AST 节点。
2. 每个 Widget 是 `Padding(child: Text.rich(textSpan))`，没有存储对原始 markdown 节点的引用。
3. `SpanNode` 树在 `build()` 后生成 `InlineSpan`，之后 `SpanNode` 本身不再被持有。

要实现"点击位置 → 对应 markdown 元素"的映射，需要：
- 在 Widget 生成阶段为每个块级元素包裹可识别的容器（如带 `Key` 或 `GestureDetector` 的 Widget）
- 或者维护一个从 Widget index → AST 节点类型的映射表

这意味着需要对 `MarkdownGenerator` 和 `WidgetVisitor` 进行较大改造。文档应明确是否接受这种改造范围。

#### 3.4.2 与 `SelectionArea` 的关系

当前实现中，`MarkdownWidget` 在 `selectable = true` 时简单地用 `SelectionArea` 包裹整个 `ListView`：

```dart
return widget.selectable
    ? SelectionArea(child: markdownWidget)
    : markdownWidget;
```

自定义选择模式是：
- **方案 A**：完全替换 `SelectionArea`，自行实现选中高亮和光标拖拽？
- **方案 B**：保留 `SelectionArea`，通过其 `contextMenuBuilder` 自定义菜单，并通过编程方式控制选区？

Flutter 3.27.4 的 `SelectionArea` 已支持 `contextMenuBuilder` 和 `onSelectionChanged`。方案 B 的实现成本显著低于方案 A，但可能无法完全满足"先不选中文字，先弹菜单"的需求（因为 `SelectionArea` 的长按默认行为是立即开始选中）。

**建议**：在需求文档中明确技术路线偏好，或者将此作为方案设计阶段的决策点。

#### 3.4.3 `MarkdownBlock` 是否需要支持

源码中有两个入口 Widget：
- `MarkdownWidget`：基于 `ListView`，可滚动
- `MarkdownBlock`：基于 `Column`，不可滚动

需求仅提到 `MarkdownWidget`，是否意味着 `MarkdownBlock` 不需要支持？如果后续需要支持，建议将选择逻辑抽取为独立的 mixin 或组合类。

### 3.5 非功能性需求缺失（P2）

#### 3.5.1 平台适配

- **移动端**：长按交互自然，无问题。
- **桌面端**：右键点击是否等效于长按？双击选词是否仍然保留？
- **Web 端**：浏览器原生的选择和右键菜单会与自定义行为冲突。

文档指定了 Flutter 3.27.4 但未说明目标平台。

#### 3.5.2 性能考量

如果为每个块级元素都包裹 `GestureDetector`，在长文档（数百个 markdown 节点）场景下，是否会影响 `ListView` 的构建性能？由于 `ListView.builder` 是懒加载的，影响应该有限，但仍值得评估。

#### 3.5.3 无障碍（Accessibility）

自定义菜单是否需要支持 `Semantics` 标注？选中状态是否需要通过 `SemanticsService` 通知屏幕阅读器？

---

### 3.6 文档结构建议（P2）

#### 3.6.1 缺少交互流程图

建议补充状态流转图，明确所有状态转换路径和触发条件。

#### 3.6.2 缺少验收标准

建议补充可量化的验收条件，例如：
1. 未开启自定义模式时，所有现有测试用例通过
2. 长按后 300ms 内弹出自定义菜单
3. 点击"选取文字"后，对应元素被完整选中（高亮覆盖元素全部文字）
4. 选中后可拖动光标调整范围
5. 点击"复制"后，剪贴板内容与选中文字一致
6. `example` 目录下有可运行的演示代码

#### 3.6.3 缺少错误/异常场景

- 空内容的 markdown 元素被长按时如何处理？
- 长按位置恰好在两个元素的边界（padding 区域）时，选中哪个元素？
- 快速连续长按不同位置时，是否有防抖机制？

## 四、与源码架构的适配性分析

基于对当前源码的阅读，以下是实现该需求时需要关注的架构适配点：

| 现有架构特征 | 对需求实现的影响 |
|---|---|
| `buildWidgets()` 返回 `List<Widget>`，每个 Widget 是 `Padding(child: Text.rich(...))` | 需要改造为可识别的容器 Widget，以支持 HitTest 定位 |
| `SpanNode` 树在 `build()` 后不再被持有 | 需要保留 SpanNode → Widget 的映射关系，或在 Widget 层记录元素类型 |
| `SelectionArea` 直接包裹整个 `ListView` | 自定义选择模式可能需要替换或深度定制 `SelectionArea` 的行为 |
| `MarkdownConfig` 通过 tag → config 映射管理配置 | 新增的选择配置不属于某个具体 tag，需要在更上层管理 |
| `WidgetVisitor` 的 `onNodeAccepted` 回调已提供节点索引 | 可复用此机制建立元素索引，但需要扩展以携带更多元素元数据 |

## 五、评审结论

| 优先级 | 数量 | 关键项 |
|---|---|---|
| **P0（阻塞开发）** | 3 | 开启方式/API 接口未定义、"正文部分"定义歧义、元素选中规则不完整 |
| **P1（影响方案设计）** | 4 | 菜单生命周期、手势冲突、触摸位置到元素的映射方案、与 SelectionArea 的关系 |
| **P2（建议补充）** | 4 | 平台适配、性能考量、验收标准、异常场景 |

**核心建议**：在进入方案设计前，优先补充 P0 级别的内容。特别是 API 接口的定义决定了整个功能的对外形态，元素选中规则的明确决定了内部实现的复杂度边界。建议以一次需求澄清会议的形式，将上述 P0 和 P1 问题逐一确认后再启动开发。
